# 岗位与项目源码匹配

## 确定分析范围

- 使用用户指定的仓库、目录或提供的源码文件。用户说「这个项目」时，确认当前工作区的项目根目录。从子目录进入时，以目标仓库根目录为报告位置，源码检查仍按用户指定的范围进行。工作区里有多个候选项目且目标不明时，请用户指定。只有附件或粘贴的源码时，以实际可读的文件为检查范围。源码无法读取时，请用户提供相关文件和项目相对路径。
- 有 JD 时，优先核对必备要求，再看加分项。只有岗位名称时，用常见职责作为通用基准，并说明依据。把岗位要求当作检索方向。两者都缺失时，询问目标岗位。
- 只读检查源码、配置、测试和已有文档。用户提供的项目介绍、历史报告和对话摘要可作为检索线索。检索时排除 `.project-role-match/`，实现结论须在当前项目的文件中重新核对。

## 先核对源码，再推荐亮点

判定证据是否足够时，参照 [源码证据契约](references/evidence-contract.md)。

1. 把要求转成可核对的问题。例如「处理并发写入」需要确认请求如何到达写入逻辑、冲突在哪里检测、冲突后会执行哪些操作。
2. 对每个候选亮点，实际打开引用文件并读到相关方法、配置或 SQL。沿真实入口追到关键实现，核对调用关系、错误分支和必要的配置。发布前确认引用都能在当前项目根目录下定位，且指向已读过的代码。能确认到文件或符号时，按实际精度引用。
3. 核对功能的接入和证据范围。依赖声明、接口定义、占位返回值、示例、测试替身和遗留代码各自只能证明它们实际呈现的内容。只有读到入口和关键业务行为才能将功能列为已实现的亮点。代码接入、当前配置启用、实际部署和线上运行分别需要对应证据。无法追到关键行为时，把该项留作证据缺口。
4. 用户明确说明某功能未实现时，从已实现亮点和面试话术中移除该功能。若当前源码出现表面冲突的片段，写明读到了什么、还缺哪段调用链，等归属和接入情况核实后再判断。例如仅找到支付相关命名、开关或占位接口时，仍需实际读到回调处理、订单状态更新及其接入证据，才能描述对应实现。
5. 性能数字、接口数量、生产规模和效果需要能定位的记录或可说明的统计方法。性能数据附上来源、场景和口径。缺少基准记录时，用源码能支持的行为描述。个人贡献和设计动机以用户确认或其提供的材料为准。

## 撰写报告

- 开头给出岗位匹配结论，再写明目标岗位、JD 或通用职责、实际检查的根目录和模块。有 Git 时记录所读版本的提交号，并注明证据是否来自未提交的改动。
- 按 JD 和项目实际覆盖的技术领域组织知识点。检索时考虑架构和调用边界、接口与业务规则、存储与一致性、并发与故障处理、安全、性能、测试、可观测性和部署等方向，按岗位调整取舍。覆盖各项有独立源码证据的关键要求，合并重复内容，证据不足的方向写进待核实事项。
- 每个知识点写清业务问题、项目做法、从入口到关键行为的执行流程、设计取舍和适用边界，再附源码证据和可口述的面试讲法。必要时引用入口、实现和配置。源码链接相对于报告目录，写入前确认都指向已读文件。
- 每个知识点通常给 3–5 道面试追问和具体答题要点。优先覆盖实现原理、设计理由、异常或边界、验证方法，按题目需要补充可替代方案。答案先说明本项目源码能证实的行为，再说明通用原理或假设条件。证据有限时保留真正有区分度的问题。
- 使用「岗位匹配总览 → 知识点详解 → 待核实事项」的结构。总览按技术领域列出知识点，详情按岗位相关性排序。正文用短段落和分级标题组织。
- 把尚未核实的接入、并发边界、运行结果和个人职责写成待确认问题。面试话术和项目摘要沿用正文的证据范围，每个技术结论回指已读源码、测量记录或用户确认。个人职责确认后再使用「我设计了」「我做过」等说法。

## 用 CLI 校验引用并交付

命令执行可用且已安装 Node.js 20 或更新版本时，使用随包 CLI。

1. 阅读 [报告输入格式](references/report-input.md)，按格式把分析结果写入临时 JSON 文件，或通过标准输入传给 CLI。每条引用提供仓库相对路径、起始行号和已读到的原文。截取足以支持判断的片段，避免将凭据或个人数据写入输入。
2. 从实际加载的 `SKILL.md` 位置找到 `bin/project-role-match.mjs`。将已核实的项目根目录作为 `--root`，临时 JSON 文件作为 `--input`。保存报告用 `write`，它会生成同名的 `.md`、独立 `.html` 和 `.receipt.json` 门禁回执三个文件。新报告默认加上 `--quality strict`；用户只要聊天回复或目标目录不可写时，改用 `check` 校验引用和质量门禁。

   ```sh
   node "<Skill目录>/bin/project-role-match.mjs" write --root "<项目根目录>" --input "<临时JSON>" --quality strict
   ```

   strict 检查每个知识点是否有 `category`、完整的 `analysis`、至少 3 道追问，以及分类覆盖是否足够。未声明 `coverage` 时默认至少覆盖 `min(3, 知识点数)` 个领域；岗位本身涉及领域较少时，在输入 JSON 用 `coverage` 声明应覆盖的领域。证据不足的领域写入 `gaps`，并包含该领域名称。

3. 引用校验或 strict 质量门禁失败时，先修正输入 JSON：引用问题回到源码核实；结构、追问或覆盖问题补齐 `category`、`analysis`、追问，或用 `coverage` 声明范围。`write` 成功后，给出 `.md`、`.html` 和 `.receipt.json` 三个实际路径，并附一两条核心结论；`quality.warnings` 非空时说明需要关注的提示。回执记录四道 gate 的状态和两个报告文件的 SHA-256，需要复查时读它，不要在报告正文重复门禁细节。需要确认报告生成后是否被改动时，运行 `verify --root <项目根目录> --receipt <回执路径>`；它重新计算两个产物的 SHA-256 和字节数，发现缺失、修改或路径越界时返回非零退出码。HTML 可直接在浏览器打开，适合自己复习或分享。报告写入项目根目录的 `.project-role-match/`，同日同岗位重名时三个文件加同一序号。`check` 成功后，在聊天中给出报告正文。

### 直接交付 Markdown

没有终端、Node.js 或随包脚本时，逐条回读源码核对引用，并在报告中说明核对方式。能在项目根目录写入文件时，把 Markdown 保存到 `.project-role-match/YYYY-MM-DD-岗位.md`，同名时追加序号；此降级路径不生成 HTML，也不生成门禁回执，HTML 和回执由随包 CLI 的 `write` 生成。没有 CLI 时也按同样的结构、追问和分类覆盖要求自检。只有聊天输出权限或用户指定聊天交付时，直接回复报告正文，引用实际读到的文件路径和函数名，能够确定行号时也附上行号。
