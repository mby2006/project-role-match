# 源码证据契约

用于判断一个岗位匹配点是否有足够证据写进报告。目标是把「源码里有什么」和「只能推测什么」分开，避免面试时被追问穿。

## 证据层级

| 层级 | 看什么 | 能证明什么 |
|---|---|---|
| 入口 | 路由注册、导出函数、CLI 命令、事件处理器、测试入口 | 功能有被调用的入口 |
| 实现 | 关键分支、数据读写、错误处理、配置读取 | 功能实际做了什么 |
| 接入 | 依赖声明、应用启动注册、迁移、环境配置 | 代码是否真正接入 |
| 运行 | 测试、基准记录、日志、部署配置 | 代码是否被验证或运行过 |

- 只读到入口或接口定义时，不能写「已实现」。
- 只有接入证据、没有关键行为时，写进待核实事项。
- 性能数字、并发能力和生产规模需要可定位的记录与统计口径；没有记录时，只描述源码能支持的行为。
- 测试替身、fixture 和示例代码只能证明它们自身，不能替代真实实现。

## 追踪步骤

1. 从用户指定的仓库根目录和真实入口开始，沿调用链读到关键行为；不要只看文件名、注释或依赖声明。
2. 同时检查成功分支、错误分支和改变行为的配置。
3. 确认功能是否已接入：路由注册、依赖注入、启动配置、迁移文件。
4. 记录实际读到的版本：有 Git 时写 commit 和未提交改动；否则写「工作区文件」。
5. 排除 `.project-role-match/` 和 `.git/`；不把生成的报告当证据。

## 判定规则

- **可写入亮点**：入口和关键实现已读；涉及接入时还有接入证据。
- **证据缺口**：只找到命名、接口、占位返回、示例或测试替身；或关键调用链缺失。
- **待核实**：并发边界、运行时行为、部署状态、性能数字、个人职责。
- 用户明确说某功能未实现时，从亮点和面试话术中移除。源码中出现表面冲突的片段时，写明读到了什么、还缺哪段调用链，再判断归属和接入情况。

## 引用写法

- 每条引用给出项目根目录相对路径（用 `/`）、从 1 开始的起始行号，以及逐行匹配的连续源码摘录。
- 摘录保留缩进，只截取支持判断的最小范围；入口、实现和配置可以分别引用。
- CLI 会逐行核对摘录；失败时回到源码重读，不要改摘录去迁就结论。
- 不把凭据、令牌或个人数据写进输入 JSON。

## 常见过度声明

- 看到依赖或配置就写「项目用了 X」，没有读调用路径。
- 看到 async 或线程池就写「支持高并发」，没有压测记录。
- 看到控制器名或占位接口就写「实现了支付回调」。
- 给出「性能提升 30%」却没有基准来源、场景和口径。
- 用户尚未确认职责时写「我设计了」。

## 写入报告时

- `finding`：只写源码能证实的做法。
- `analysis.flow`：入口到关键行为的真实调用顺序。
- `analysis.tradeoffs`：源码可见或被用户确认的设计取舍。
- `analysis.limits`：这段代码不能证明的边界。
- `interview`：只用前面证据范围内的结论。
- `gaps`：接入、并发、运行结果、个人职责等未核实项。
- `questions`：答案先讲本项目源码能证实的行为，再讲通用原理或假设条件。
