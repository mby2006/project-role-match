重复预约处理

对应岗位要求数据库约束与接口重试

项目做法

样例在路由注册函数中定义预约接口。写入时以用户和时段为组合键，冲突时走更新分支并返回预约 ID。

执行流程

注册函数定义 POST /bookings。处理器从请求体取出用户和时段 ID，把它们作为参数提交给 PostgreSQL。写入成功时返回新 ID；命中组合唯一约束时更新冲突行并返回已有 ID。处理器将数据库返回值作为 JSON 发出。

设计取舍

把重复判断放在数据库里，使不同请求处理器共享同一条约束。使用 DO UPDATE 可以直接用 RETURNING 取已有 ID，但即使列值相同也走更新路径，需要考虑写放大和触发器副作用。

适用边界

约束只覆盖同一用户和同一时段，无法证明一个时段只能被一人预约。源码也没有提供并发压测结果或数据库异常到 HTTP 状态码的映射。

面试讲法

可以讲同一用户重试预约同一时段时，唯一约束怎样阻止第二条记录，以及 SQL 怎样返回预约 ID。

面试追问与答题要点

Q1为什么不先查有没有预约，再决定要不要插入？

两个请求可能同时查不到记录，然后都发起写入。示例在数据库用 UNIQUE (user_id, slot_id) 保证组合键唯一，并用 ON CONFLICT 定义冲突时的行为。

Q2为什么用 DO UPDATE，改成 DO NOTHING 会怎样？

这里要在一条语句里返回预约 ID。DO NOTHING 跳过冲突行，RETURNING 不会返回该行的 ID。DO UPDATE 可以返回已有 ID，代价是冲突时走更新路径。

Q3如何验证重复请求的行为？

在使用该建表定义的数据库上，同时提交多次相同用户和时段的请求，断言最终只有一行且成功响应的 ID 一致。再用两个不同用户请求同一时段，核实组合键允许这两条记录。
